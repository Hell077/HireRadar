# План реализации MVP бэкенда

Статус: этапы MVP 0–8 завершены; дальнейшие задачи перечислены в разделе «Отложено после MVP». Источник: `apps/backend/agent.md`. В этом плане зафиксированы порядок работ и критерии приёмки. Этап считается завершённым только после прохождения всех его критериев.

## Принятые решения

- Оставить бэкенд модульным монолитом на Go с границами между доменом, приложением и адаптерами. Код домена не должен импортировать транспортные пакеты или пакеты инфраструктуры; сценарии приложения зависят от портов.
- Использовать существующий HTTP-стек Fiber + Huma и его контракт OpenAPI. Выбор `net/http` + chi из исходного архитектурного документа заменён этим решением. Детали транспорта должны оставаться внутри HTTP-адаптера.
- Собирать бэкенд на Go 1.27.0. По возможности применять нововведения Go 1.26 (`new(expression)` и списки параметров типов с самоссылочными параметрами), а также Go 1.27 (методы с параметрами типов, вложенные селекторы полей в ключах литералов структур и более широкое выведение типов generic-функций), если это упрощает код. Generic-методы не могут реализовывать методы интерфейсов, объявленные с параметрами типов.
- Использовать PostgreSQL как источник истины. Для хранения и миграций использовать pgx и goose; Redis — для очередей, кэширования и временного состояния. Хранить резюме в приватном S3-совместимом хранилище за портом хранения.
- Запускать API и фоновые службы из одного backend-бинарника: каждая служба работает в отдельной контролируемой горутине с общим жизненным циклом процесса. Операторский API показывает состояние, последнюю ошибку и число запусков, позволяет остановить или перезапустить службу.
- Сохранять исходные данные источника до нормализации. Фоновые задачи должны быть идемпотентными, а события между модулями — публиковаться через транзакционный outbox.
- Для MVP использовать детерминированную проверку доступности и подбор вакансий. ИИ и семантическое ранжирование оставить на будущее. Неизвестное местоположение должно оставаться неизвестным; `remote` не означает доступность вакансии по всему миру.

## Последовательность работ

Каждый этап — отдельное изменение для ревью со своей миграцией, тестами, обновлением документации и рабочим контрактом API, где это применимо. Не создавать пустые модули заранее.

## Текущее состояние реализации

- Этап 0 завершён: версия модуля Go 1.27.0, проверка конфигурации, JSON-логи и идентификаторы запросов, корректное завершение API, клиенты PostgreSQL и Redis, `/api/v1/ready` с проверкой зависимостей и первая миграция goose для outbox реализованы и проверены в Docker. API применяет миграции до начала приёма запросов.
- В режиме разработки можно запустить API без внешних служб, чтобы просматривать Huma OpenAPI. В этом режиме readiness и конечные точки аутентификации возвращают 503. Для production требуются `DATABASE_URL`, `REDIS_URL` и `JWT_PRIVATE_KEY` — ключ Ed25519 длиной 32 байта в base64.
- При запуске API применяет миграции, удерживая advisory lock PostgreSQL. Для локального запуска используйте Go 1.27.0; генератор клиентов в корне репозитория принимает `GO_BINARY`, если команда `go` по умолчанию указывает на другую версию.
- Проверка в Docker охватила применение миграций самим API и идемпотентный перезапуск, готовность PostgreSQL/Redis, создание бакета RustFS, отказ и восстановление Redis, а также остановку API. Этап 1 завершён: реализованы регистрация, хеширование Argon2id, access-токены Ed25519, ротация refresh-токенов, выход, подтверждение почты, сброс пароля, лимиты аутентификации по IP на Redis и SMTP outbox-воркер. В Docker-стеке почта направляется в Mailpit; страницы регистрации, входа, подтверждения адреса, запроса и сброса пароля отправляют запросы в API. При входе токены сохраняются в HTTP-only cookies. Автоматизированные интеграционные тесты PostgreSQL проверяют дубликаты, истечение срока и повторное использование токенов, выход и отзыв сессий при сбросе пароля. Сброс пароля отзывает refresh-сессии; ранее выданные access-токены действуют до окончания своего 15-минутного срока. Этапы 2–8 завершены.
- Этап 2 завершён: миграции 00003–00004 добавляют профиль кандидата, нормализованные навыки и псевдонимы, желаемые должности, предпочтения по вакансиям и источникам. Для всех пяти ресурсов доступны аутентифицированные API `GET` и `PUT`. Проверка данных и владения выполняется на основе bearer-токена Ed25519; каждое изменённое значение записывает `profile.changed` в той же транзакции PostgreSQL, а неизменённые данные события не создают. Интеграционные тесты PostgreSQL проверяют правила записи события и сохранения. ID предпочтений источников — нормализованные slug-строки; теперь они связаны с реестром источников.
- Этап 3 завершён: миграции 00005–00006 хранят метаданные приватных резюме, разобранный текст и результаты, состояние повторных попыток и предложения для проверки. Аутентифицированные Huma-маршруты позволяют просматривать список, создавать presigned URL для загрузки, подтверждать завершение, получать короткоживущие ссылки на скачивание, удалять резюме, читать результаты анализа и принимать или отклонять предложения. Встроенный worker резюме в горутине backend безопасно захватывает загруженные резюме, скачивает их из RustFS, извлекает текст из текстовых PDF с ограничениями на число страниц, потоки, глифы, время и размер, находит навыки из каталога и строки, похожие на должности, а затем транзакционно сохраняет результат и предложения. Завершение загрузки и обработка идемпотентны; подтверждение предложения обновляет навыки или должности и записывает `profile.changed` в той же транзакции, а разбор документа сам по себе не меняет профиль. Интеграционные тесты PostgreSQL проверяют владение, дедупликацию outbox, обработку и транзакции проверки предложений; Docker-проверка прошла от загрузки до обработки воркером и проверки предложения. OCR для сканированных PDF пока нет; извлечение компаний, образования и языков отложено.
- Этап 4 завершён: миграции 00007–00008 добавляют реестр источников, тип источника GitHub, историю синхронизаций и неизменяемые снимки исходных вакансий. Ограниченный встроенный source worker забирает источники, готовые к синхронизации, через `FOR UPDATE SKIP LOCKED`, изолирует сбои источников, повторяет попытку через минуту и транзакционно сохраняет исходные снимки с хешами содержимого и счётчиками синхронизации. Публичные адаптеры Greenhouse, Lever, Ashby и GitHub сопоставляют стабильные ID и сохраняют JSON исходной вакансии; включённые источники доступны через `GET /api/v1/sources`. Контрактные тесты проверяют сопоставление данных, пагинацию, фильтрацию pull request, некорректную конфигурацию источника, исходные данные и ошибки HTTP; интеграционные тесты PostgreSQL проверяют версии снимков, счётчики и повтор после сбоя. Управление источниками для операторов добавлено на этапе 8. Этап 5 следует за сбором вакансий из источников.
- Этап 5 завершён: миграции 00009–00011 добавляют нормализованные компании и вакансии, ссылки на вакансии из разных источников, доступность, fingerprint для дедупликации, отложенное закрытие, грейды, связи вакансий с навыками каталога и nullable-поля диапазона зарплат. Синхронизация источников транзакционно сохраняет исходные и нормализованные записи вместе с событиями `job.created`/`job.updated`. Реализованы очистка данных компаний, заголовков и описаний, канонизация URL, дедупликация по fingerprint, обновление с учётом приоритета источника, определение доступности для Казахстана (значение `unknown` сохраняет неопределённость) и закрытие после двух успешных синхронизаций, в которых вакансия отсутствовала. Грейд определяется консервативно по терминам в заголовке; навыки ищутся по целым словам среди навыков профиля и их псевдонимов, дубли псевдонимов объединяются, а неоднозначные совпадения не помечаются как явно обязательные. Разбор зарплат принимает только подписанные диапазоны с распознанной валютой, сохраняет указанный период оплаты и оставляет пустыми неоднозначные или некорректные значения. География распознаёт распространённые названия стран, выбранные псевдонимы городов и корректные коды стран из двух заглавных букв; широкие регионы, например APAC, остаются `unknown` для проверки доступности в Казахстане. `GET /api/v1/jobs` и `GET /api/v1/jobs/{id}` поддерживают курсорную пагинацию и возвращают зарплату, грейд, найденные навыки и распознанные коды стран; `GET /api/v1/sources` сообщает последнюю синхронизацию и счётчики, не раскрывая конфигурацию источника или внутренние тексты ошибок. Интеграционные тесты проверяют доступность в Казахстане, США и других странах, фильтры курсора, дубли источников, приоритет официального источника, разбор и сохранение зарплат, извлечение навыков, грейды, отложенное закрытие и безопасный мониторинг источников. Более широкий список городов и проверка доступности по часовым поясам остаются дальнейшими улучшениями.
- Этап 6 завершён: детерминированный движок подбора до вычисления оценки применяет жёсткие фильтры по статусу вакансии, доступности в стране, исключённым странам, разрешённым регионам, типу удалённой работы, типу занятости, давности публикации, сопоставимому минимальному уровню зарплаты и минимальному баллу. Для подходящих вакансий рассчитываются взвешенные компоненты навыков, желаемой должности, грейда, местоположения и зарплаты; значения по умолчанию можно заменить проверенной конфигурацией весов на 100 баллов. Миграция 00012 хранит актуальное совпадение пользователя и вакансии с компонентами оценки. Предварительный отбор PostgreSQL учитывает предпочтения профиля и отключённые источники; аутентифицированный `POST /api/v1/matches/refresh` пересчитывает и сохраняет результаты, а `GET /api/v1/matches` возвращает список. Повторный пересчёт идемпотентен и удаляет устаревшие совпадения. Встроенный matching worker забирает события изменения профиля и создания, обновления или закрытия вакансии через `FOR UPDATE SKIP LOCKED`, пересчитывает результат для нужного пользователя или кандидатов, подтверждает успешную обработку и повторяет сбойные попытки с экспоненциальной задержкой. Тесты PostgreSQL проверяют идемпотентность пересчёта, объяснения оценки, повторный подбор после изменения профиля, подбор при появлении вакансии, повторную доставку события, расписание повторных попыток и удаление устаревших совпадений. Доставка уведомлений реализована на этапе 7.
- Этап 7 завершён: миграция 00013 добавляет хешированные одноразовые токены привязки Telegram, связанные аккаунты, настройки уведомлений, состояние дедуплицированной доставки, сохранённые вакансии и обратную связь. Аутентифицированные маршруты `GET /api/v1/telegram`, `POST /api/v1/telegram/link`, `DELETE /api/v1/telegram` и маршруты настроек уведомлений управляют подключением; `POST /webhooks/telegram` проверяет секретный заголовок Telegram и принимает `/start` из личного чата и callback-действия обратной связи. При создании совпадения запись `match.created` добавляется в outbox в той же транзакции. Воркер уведомлений учитывает минимальный балл, тихие часы в часовом поясе IANA пользователя, немедленную доставку или ближайшее время дайджеста — 09:00 по местному времени — и дневные лимиты. В MVP всё ещё отправляется отдельное сообщение для каждой вакансии. Сообщения содержат сведения о вакансии и кнопки обратной связи. Неудачные доставки повторяются с экспоненциальной задержкой; после 12 попыток статус меняется на `failed`. Повторные события outbox не создают дубликаты уведомлений; callback-действия «скрыть» и «откликнулся» проверяют владение совпадением и исключают его из будущих результатов. Тесты PostgreSQL и API проверяют повторное использование токена, сохранение настроек, вычисление расписания, аутентификацию webhook, дедупликацию уведомлений, доставку через Telegram, повторные попытки, очередь невосстановимых ошибок и владение обратной связью. Воркер находится в профиле Compose `telegram`; если задан `TELEGRAM_WEBHOOK_URL`, API на старте настраивает webhook Telegram.
- Этап 8 завершён: аутентифицированный `GET /api/v1/saved-jobs` возвращает сохранённые вакансии пользователя с их данными, а `DELETE /api/v1/saved-jobs/{id}` удаляет вакансию из списка. `POST /api/v1/jobs/{id}/feedback` принимает `hide` или `applied`, проверяет, что вакансия является текущим совпадением этого пользователя, сохраняет обратную связь, отменяет ожидающие уведомления и удаляет совпадение в одной транзакции. API предоставляет `/metrics` со счётчиками запросов и их суммарной длительностью по методу и статусу; идентификаторы запросов и трассировок попадают в структурированные логи. Операторские маршруты источников показывают состояние всех источников, меняют флаг активности, приоритет и интервал опроса, запрашивают внеплановую синхронизацию и возвращают журнал аудита. Для них требуется случайный `OPERATOR_API_TOKEN` длиной не менее 32 символов; конфигурация источника не раскрывается. Сквозной тест PostgreSQL проводит тестовый источник через сохранение исходных данных, нормализацию, подбор, планирование уведомления, пересоздание воркера и однократную доставку. Серверные Fiber spans принимают контекст трассировки W3C и экспортируются по OTLP/HTTP, если задан `OTEL_EXPORTER_OTLP_ENDPOINT` или `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`. Ниже описаны процедуры для Docker, Railway и миграций expand/contract.
- Веб-приложение использует конечные точки идентификации и профиля кандидата для регистрации, входа, ротации refresh-токена, выхода, подтверждения email, сброса пароля, чтения и изменения профиля, а также чтения и замены навыков. Экраны резюме, вакансий, сохранённых вакансий, уведомлений и Telegram пока остаются демонстрационными; API привязки Telegram, настроек уведомлений и сохранённых вакансий готово для подключения интерфейса.
- Dockerfile бэкенда использует Go 1.27.0. Корневой `docker-compose.yml` запускает API, PostgreSQL, Redis, RustFS и одноразовый контейнер AWS CLI для инициализации бакета. API получает настройки S3 для приватной загрузки резюме; инициализатор бакета настраивает CORS для локальных веб-доменов.

## Локальный Docker-стек

1. Скопируйте `.env.docker.example` в `.env` и замените тестовые учётные данные. Файл `.env` исключён из Git.
2. В корне репозитория выполните `docker compose up --build -d`. PostgreSQL, Redis и RustFS останутся в сети Compose; единый контейнер backend запустит HTTP API и настроенные фоновые службы в горутинах. API будет доступен по `http://127.0.0.1:8080`, S3 API и консоль RustFS — на локальных портах 9000 и 9001, а локальный почтовый ящик Mailpit — на `http://127.0.0.1:8025`. Telegram необязателен: укажите `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` и `TELEGRAM_WEBHOOK_SECRET`; `TELEGRAM_WEBHOOK_URL` нужен для HTTPS webhook.
3. Проверьте `http://127.0.0.1:8080/api/v1/ready`: адрес вернёт 200 после того, как backend применит миграции и PostgreSQL с Redis ответят на запросы. Все фоновые службы используют ту же базу и запускаются внутри процесса API. Их состояния смотрите через `GET /api/v1/admin/services`, а логи — `docker compose logs --tail=200 api rustfs-init`. Если Next.js работает не на `http://localhost:3000`, задайте `APP_PUBLIC_URL` для ссылок в письмах; если API доступен не по `http://127.0.0.1:8080`, задайте `API_BASE_URL` для сервера Next.js.
4. Запустите все тесты бэкенда против этого стека командой `docker run --rm --network hireradar_default --mount type=bind,src="$PWD/apps/backend",dst=/src,readonly -w /src -e PGPASSWORD="$POSTGRES_PASSWORD" -e TEST_DATABASE_URL='postgres://hireradar@postgres:5432/hireradar?sslmode=disable' golang:1.27.0-alpine3.24 go test ./... -count=1`.

### Релизы и изменения схемы

Для локального релиза выполните `docker compose up --build -d`, дождитесь ответа `/api/v1/ready`, затем проверьте последние логи командой `docker compose logs --tail=200 api`. Собирайте `/metrics` из сети API и ищите в JSON-логах соответствующие `X-Request-ID` и `trace_id`. Метрики хранятся только в памяти процесса и сбрасываются при перезапуске; до настройки общего сервиса телеметрии они подходят для сбора с одного экземпляра. Задайте `OTEL_EXPORTER_OTLP_ENDPOINT` — базовый URL коллектора OTLP/HTTP — чтобы экспортировать трассы запросов API; в ответе будет заголовок `X-Trace-ID`.

Перед использованием операторских маршрутов задайте в `.env` случайный `OPERATOR_API_TOKEN` длиной не менее 32 символов (шаблон генерации: `openssl rand -hex 32`). Этот токен нужен также для контроля фоновых служб. Передавайте его в заголовке `X-Operator-Token` для `GET /api/v1/admin/sources`, `PUT /api/v1/admin/sources/{id}` с телом `{"enabled":true,"priority":100,"sync_interval_seconds":900}`, `POST /api/v1/admin/sources/{id}/sync` и `GET /api/v1/admin/sources/audit`. Для управления службами используйте `GET /api/v1/admin/services` и `POST /api/v1/admin/services/{name}` с JSON-телом `{"action":"start"}`, `{"action":"stop"}` или `{"action":"restart"}`. Список имён: `source`, `matching`, `notification`, `email`, `resume`. Передавайте `X-Operator-Token`; статусы включают `starting`, `running`, `stopping`, `stopped`, `failed` и `disabled`, а ответ показывает последнее сообщение об ошибке и число запусков (счётчик включает первый старт). Токен оператора отдельный от access-токенов кандидатов; для его ротации измените значение в окружении деплоя.

Для Railway сначала создайте PostgreSQL, Redis и приватный S3-совместимый бакет. Настройте переменные окружения каждого сервиса и один раз свяжите репозиторий командой `railway link`. Разверните единый backend из каталога бэкенда командой `railway up ./apps/backend --service hireradar-api`; он запускает HTTP API и настроенные фоновые службы внутри одного процесса. Отдельные Railway-сервисы для воркеров не требуются. Убедитесь, что `/api/v1/ready` отвечает, и проверьте логи деплоя до включения трафика источников. CLI Railway загружает переданный путь и использует выбранный сервис; переменные окружения единого backend задаются в проекте Railway.

Для каждой production-миграции используйте подход expand/contract: (1) добавьте nullable-столбцы, новые таблицы или совместимые индексы, не удаляя старые поля; (2) разверните код, который читает старый и новый форматы и при необходимости записывает данные в оба; (3) заполните новые данные небольшими пакетами и проверьте количество записей; (4) переключите чтение после того, как все экземпляры смогут работать с новой схемой; (5) удалите устаревшие столбцы или ограничения отдельным релизом, когда старый код уже полностью остановлен. Сейчас API применяет миграции при старте, удерживая advisory lock PostgreSQL, поэтому миграции должны оставаться совместимыми во время поэтапного обновления API. Не совмещайте удаление схемы с первым релизом, в котором код перестал использовать старую схему.

## Порядок работы с данными и зависимостями

1. Добавляйте миграции вместе с соответствующим агрегатом; обеспечивайте уникальность email, названий навыков, связей «источник/внешний ID», совпадений пользователя и вакансии, сохранённых вакансий и идентификаторов уведомлений на уровне БД. Сохраняйте совместимость миграций при поэтапном обновлении.
2. Сначала определяйте порты для сценариев использования, затем реализуйте адаптеры PostgreSQL, Redis, S3, источников и Telegram. Явно объявляйте зависимости в каждом исполняемом приложении.
3. Продумывайте границы транзакций при сохранении курсора источника, запуска синхронизации, исходных данных, нормализованной вакансии и события outbox. Сбой на любом этапе должен допускать повторную обработку без потери исходной записи и дублирования последующих эффектов.
4. Публикуйте изменения API в OpenAPI Huma и обновляйте типы веб-клиента в том же изменении, что и конечную точку.

### Добавление ATS-источника на этапе 4

Источники хранятся в PostgreSQL, а source worker начинает опрашивать их сразу после включения записи. В объекте `config` поле `board` содержит slug публичной доски вакансий ATS; поле `page_size` при необходимости задаёт размер страницы Lever (1–100). Например, после применения миграций можно добавить одобренную оператором доску:

```sql
INSERT INTO sources (id, name, source_type, company_name, config)
VALUES ('acme-greenhouse', 'Вакансии Acme', 'greenhouse', 'Acme', '{"board":"acme"}');
```

Используйте `source_type` `greenhouse`, `lever` или `ashby`, а в `board` укажите slug доски соответствующего провайдера. Для публичных репозиториев GitHub с вакансиями задайте `source_type='github'` и объект `config` с полями `owner`, `repo`, необязательными `labels` и `page_size` (1–100). Добавляйте только публичные списки вакансий, предназначенные для поиска работы.

## Проверки для каждого этапа

- В каталоге `apps/backend` запускайте форматирование Go, `go vet ./...`, `go test ./...` и `go build ./...`; при появлении систем хранения и адаптеров добавляйте интеграционные тесты.
- При изменении сгенерированных контрактов API запускайте соответствующую проверку типов и сборку веб-приложения.
- До деплоя проверяйте применение и откат миграций, а также изменения контрактов API. На этапе 8 проверьте весь путь от сбора вакансии до отправки уведомления.
