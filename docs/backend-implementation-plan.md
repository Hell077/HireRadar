# Backend MVP implementation plan

Status: implementation in progress. Source: `apps/backend/agent.md`. This plan records the order of work and acceptance gates; a milestone is complete only when its full gate passes.

## Accepted decisions

- Keep the backend as a Go modular monolith with domain, application, and adapter boundaries. Domain code must not import transport or infrastructure packages; application use cases depend on ports.
- Use the existing Fiber + Huma HTTP stack and its OpenAPI contract. The `net/http` + chi choice in the architecture source is superseded by this decision. Keep transport details inside the HTTP adapter.
- Target Go 1.27.0 for backend builds. Consider Go 1.26 language additions (`new(expression)` and self-referential generic type parameter lists) and Go 1.27 additions (generic methods, nested field-selector keys in struct literals, and broader generic function inference) when they make an implementation clearer. Generic methods cannot satisfy interface methods that declare type parameters.
- PostgreSQL is the source of truth. Use pgx and goose for persistence and migrations; Redis supports queues, caching, and temporary state. Store resumes privately behind an S3-compatible storage port.
- Run API, worker, scheduler, and Telegram responsibilities as separately deployable executables that share domain and application packages. Start with one bounded worker implementation and split deployment capacity when needed.
- Store raw source payloads before normalization. Make background jobs idempotent and publish cross-module events through a transactional outbox.
- Use deterministic eligibility and matching for the MVP. AI and semantic ranking are later extensions; an unknown location must remain unknown, and `remote` does not imply worldwide eligibility.

## Current implementation state

- Milestone 0 is complete: Go 1.27.0 module version, validated environment configuration, JSON logs and request IDs, graceful API shutdown, PostgreSQL and Redis clients, dependency-aware `/api/v1/ready`, and the first goose outbox migration are implemented and verified in Docker. The API applies migrations before it begins listening.
- Development can start without external services to expose Huma OpenAPI. In this mode readiness returns 503 and auth endpoints return 503. Production startup requires `DATABASE_URL`, `REDIS_URL`, and a base64-encoded 32-byte Ed25519 `JWT_PRIVATE_KEY`.
- The API applies migrations at startup while holding a PostgreSQL advisory lock. Use a Go 1.27.0 executable for local runs; the root client generator accepts `GO_BINARY` when the default `go` command points to another version.
- Docker verification covered API-run migration and idempotent restart, PostgreSQL/Redis readiness, RustFS bucket creation, Redis failure and recovery, and API shutdown. Milestone 1 is complete: registration, Argon2id hashing, Ed25519 access tokens, refresh rotation, logout, email verification, password reset, Redis-backed per-IP auth rate limits, and an SMTP outbox worker are implemented. The Docker stack routes email to Mailpit; the web registration, sign-in, verification, forgot-password, and reset-password pages submit to the API. Sign-in stores tokens in HTTP-only cookies. Automated PostgreSQL integration tests cover duplicate email, token expiration and replay, logout, and reset-triggered session revocation. Password reset revokes refresh sessions; previously issued 15-minute access tokens remain valid until expiry. Milestones 2–4, 6, and 7 are complete; milestone 5 is in progress and milestone 8 is in progress.
- Milestone 2 is complete: migrations 00003–00004 add candidate profile, normalized skills and aliases, desired positions, job preferences, and per-source preferences. Authenticated `GET` and `PUT` APIs cover all five resources. Validation and ownership derive from the Ed25519 bearer token; each changed resource writes `profile.changed` in the same PostgreSQL transaction, and unchanged replacements emit no event. Profile PostgreSQL integration tests cover these event and persistence rules. Source preference IDs are normalized slugs; they will connect to the source registry when that milestone is implemented.
- Milestone 3 is complete: migrations 00005–00006 store private resume metadata, parsed text/results, retry state, and reviewable suggestions. Authenticated Huma routes list, create presigned uploads, verify completion, return short-lived downloads, delete, read analysis, and accept/reject suggestions. A separate Docker `resume-worker` claims uploaded resumes safely, downloads from RustFS, extracts text from text-based PDFs with page/stream/glyph/time/size limits, detects catalogued skills and role-like lines, and writes parsed data plus suggestions transactionally. Completion and processing are idempotent; acceptance updates skills or positions and emits `profile.changed` in the same transaction, while parsing never changes the profile. PostgreSQL integration tests cover ownership, outbox deduplication, processing, and review transactions; Docker verified upload through worker and suggestion review. Scanned PDFs have no OCR support yet, and extraction of companies, education, and languages remains future parser work.
- Milestone 4 is complete: migrations 00007–00008 add the source registry, GitHub source type, sync run history, and immutable raw-job snapshots. A bounded `source-worker` claims due sources with `FOR UPDATE SKIP LOCKED`, isolates source failures, retries after one minute, and stores raw job snapshots with content hashes and sync counters transactionally. Greenhouse, Lever, Ashby, and GitHub public-source adapters map stable IDs and preserve upstream job JSON; enabled sources are listed at `GET /api/v1/sources`. Contract tests cover mapping, pagination, pull-request filtering, invalid source config, raw payloads, and HTTP failures; PostgreSQL integration verifies snapshot versions, counters, and failure retry. Source rows are provisioned directly in PostgreSQL for now; admin CRUD and operational replay controls remain in milestone 8. Milestone 5 follows source ingestion.
- Milestone 5 is in progress: migrations 00009–00011 add normalized companies, jobs, multi-source references, eligibility, dedupe fingerprints, delayed closure state, seniority, job-to-catalog-skill links, and nullable salary range fields. Source sync persists raw and normalized records plus `job.created`/`job.updated` events in one transaction. Company/title/description cleanup, canonical URL and fingerprint dedupe, source-priority updates, Kazakhstan eligibility (`unknown` stays distinct), and closure after two successful missing syncs are implemented. Seniority is conservatively classified from title terms; skills are matched on whole terms against profile skills and aliases, with duplicate aliases collapsed and uncertain matches marked as not explicitly required. Salary parsing accepts only labeled ranges with a recognized currency, keeps the stated pay period, and leaves ambiguous or malformed values empty. Location recognition covers common country names, selected city aliases, and recognized uppercase two-letter country codes; broad regions such as APAC remain `unknown` for Kazakhstan eligibility. `GET /api/v1/jobs` and `GET /api/v1/jobs/{id}` provide cursor pagination with salary, seniority, detected skills, and recognized country codes; `GET /api/v1/sources` reports the latest sync status and counts without exposing source config or internal error details. Integration tests cover Kazakhstan, US and additional country eligibility, cursor filters, duplicate sources, official-source priority, salary parsing and persistence, skill extraction, seniority, delayed closure, and safe source monitoring. Complete global city aliases and timezone-based eligibility remain planned.
- Milestone 6 is complete: a deterministic matching engine applies job status, country eligibility, excluded-country, allowed-region, remote-policy, employment-type, age, comparable minimum-salary, and minimum-score filters before returning any score. Eligible jobs receive weighted skill, desired-position, seniority, location, and salary components with defaults that can be overridden by a validated 100-point weight configuration. Migration 00012 stores one current match per user/job with score components. PostgreSQL preselection applies profile preferences and source opt-outs; authenticated `POST /api/v1/matches/refresh` recalculates and saves results, while `GET /api/v1/matches` lists them. Repeat refresh is idempotent and removes stale matches. The Docker `matching-worker` claims profile and job create/update/close events with `FOR UPDATE SKIP LOCKED`, refreshes the affected owner or candidate set, acknowledges successful processing, and retries failures with exponential backoff. PostgreSQL tests cover refresh idempotency, explanations, profile-change refresh, new-job fan-out, duplicate delivery, retry scheduling, and stale-result cleanup. Notification delivery begins in milestone 7.
- Milestone 7 is complete: migration 00013 adds hashed, single-use Telegram linking tokens, connected accounts, notification preferences and deduplicated delivery state, saved jobs, and feedback storage. Authenticated `GET /api/v1/telegram`, `POST /api/v1/telegram/link`, `DELETE /api/v1/telegram`, and notification preference routes manage the connection; `POST /webhooks/telegram` checks Telegram's secret header and accepts private-chat `/start` and feedback callbacks. Matching inserts `match.created` into the outbox with new match rows in the same transaction. The notification worker applies minimum score, quiet hours in the user's IANA timezone, immediate delivery or the next 09:00 local delivery window in digest mode, and daily caps; this MVP still sends one message per job. Messages include job details and feedback buttons. Failed deliveries use exponential backoff and move to `failed` after 12 attempts; duplicate outbox events do not duplicate notification rows, and hidden/applied callbacks are checked against current match ownership and remove the match from future results. PostgreSQL and API tests cover token reuse, preference persistence, schedule calculation, webhook authentication, notification deduplication, Telegram delivery/retries/dead-letter state, and feedback ownership. The worker is in the Compose `telegram` profile; the API configures Telegram's webhook on startup when `TELEGRAM_WEBHOOK_URL` is set.
- Milestone 8 is in progress: authenticated `GET /api/v1/saved-jobs` lists a user's saved jobs with vacancy details, and `DELETE /api/v1/saved-jobs/{id}` removes one. `POST /api/v1/jobs/{id}/feedback` accepts `hide` or `applied`, confirms the job is a current match owned by the authenticated user, records feedback, cancels pending notifications, and removes the match transactionally. The API exposes `/metrics` with request counters and cumulative latency by method/status; request IDs are included in structured logs. Remaining scope includes admin source controls and audit trail, distributed tracing, expand/contract migration procedures, and the end-to-end restart-resume gate.
- The web application calls identity and candidate-profile endpoints for registration, login, refresh rotation, logout, email verification, password reset, profile read/update, and skill read/replace. Resume, vacancy, saved-job, notification, and Telegram screens remain presentation-only; Telegram linking, notification preference, and saved-job APIs are available for frontend integration.
- The backend Dockerfile uses Go 1.27.0. The root `docker-compose.yml` runs the API, PostgreSQL, Redis, RustFS, and a one-shot AWS CLI bucket initializer. The API consumes S3 configuration for private resume uploads; the bucket initializer configures browser CORS for local web origins.

## Local Docker stack

1. Copy `.env.docker.example` to `.env` and replace its placeholder credentials. The `.env` file is ignored by Git.
2. Run `docker compose up --build -d` at the repository root. PostgreSQL, Redis, and RustFS stay on the Compose network; the API is available at `http://127.0.0.1:8080`, RustFS exposes its S3 API and console on localhost ports 9000 and 9001, and Mailpit's local inbox is at `http://127.0.0.1:8025`. Telegram is optional: set all four `TELEGRAM_*` values in `.env`, with an HTTPS public URL in `TELEGRAM_WEBHOOK_URL`, then run `docker compose --profile telegram up --build -d` to start its delivery worker.
3. Check `http://127.0.0.1:8080/api/v1/ready`; it returns 200 after the API applies migrations and PostgreSQL and Redis respond. The email, resume, source, and matching workers start after the API is healthy and do not run migrations. When the Telegram profile is enabled, its worker also uses the API's migrated database. Use `docker compose logs api email-worker resume-worker source-worker matching-worker rustfs-init` and, when enabled, `docker compose logs notification-worker` to inspect startup or delivery failures. When Next.js is not on `http://localhost:3000`, set `APP_PUBLIC_URL` for email links; set `API_BASE_URL` for the Next.js server when the API is not on `http://127.0.0.1:8080`.
4. Run all backend tests against this stack with `docker run --rm --network hireradar_default --mount type=bind,src="$PWD/apps/backend",dst=/src,readonly -w /src -e PGPASSWORD="$POSTGRES_PASSWORD" -e TEST_DATABASE_URL='postgres://hireradar@postgres:5432/hireradar?sslmode=disable' golang:1.27.0-alpine3.24 go test ./... -count=1`.

### Release and schema changes

For local releases, run `docker compose up --build -d`, wait for `/api/v1/ready`, then inspect `docker compose logs --tail=200 api source-worker matching-worker email-worker resume-worker`. Scrape `/metrics` from the API network and use `X-Request-ID` correlation in JSON logs. Metrics are process-local and reset on restart; they are intended for single-instance scraping until a shared telemetry backend is configured.

For Railway, provision PostgreSQL, Redis, and a private S3-compatible bucket first. Configure each service's variables and link the repository once with `railway link`. Deploy the API from the backend directory with `railway up ./apps/backend --service hireradar-api`; create worker services from the same Dockerfile and set their start commands to `/app/source-worker`, `/app/matching-worker`, `/app/email-worker`, `/app/resume-worker`, or `/app/notification-worker` as needed, then deploy each with `railway up ./apps/backend --service <service-name>`. Confirm the API's `/api/v1/ready` and review deployment logs before enabling source traffic. Railway's CLI deploys the supplied path and service selector; each service's runtime command and variables are configured in the Railway project.

Use expand/contract for every production migration: (1) add nullable columns, new tables, or compatible indexes without removing old fields; (2) deploy code that can read old and new forms and dual-write when required; (3) backfill in bounded batches and verify counts; (4) switch reads after all instances understand the new form; (5) remove obsolete columns or constraints in a later release after old code is fully drained. The API currently applies goose migrations at startup under a PostgreSQL advisory lock, so migrations must be safe while API instances roll. Never combine destructive schema removal with the first code release that stops using the old schema.

## Data and dependency order

1. Introduce migrations alongside each aggregate, with database uniqueness for email, skill names, source/external references, user/job matches, saved jobs, and notification identity. Keep migrations compatible with rolling deployments.
2. Define ports around use cases, then implement PostgreSQL, Redis, S3, source, and Telegram adapters. Compose dependencies explicitly in each executable.
3. Persist the source cursor, sync run, raw payload, normalized job, and outbox event in deliberate transaction boundaries. A failed stage must be retryable without losing a raw job or duplicating a later effect.
4. Publish API changes through Huma's OpenAPI output and update generated web types in the same change as the endpoint.

### Provisioning an ATS source during milestone 4

Sources are stored in PostgreSQL and the source worker starts polling as soon as a row is enabled. The `config` object uses `board` for the public ATS board slug; `page_size` optionally sets Lever's page size (1–100). For example, after applying migrations, insert an operator-approved board with:

```sql
INSERT INTO sources (id, name, source_type, company_name, config)
VALUES ('acme-greenhouse', 'Acme careers', 'greenhouse', 'Acme', '{"board":"acme"}');
```

Use `source_type` `greenhouse`, `lever`, or `ashby` and set `board` to that provider's board slug. For public GitHub issue repositories, use `source_type='github'` and a config object with `owner`, `repo`, optional `labels`, and optional `page_size` (1–100). Only add public listings intended for job discovery.

## Deferred after MVP

Keep pgvector and semantic ranking, AI analysis, additional ATS adapters, advanced source discovery, email/digest delivery, analytics, and automatic applications out of the MVP. Add them after the deterministic pipeline is working and measured.
